## FR1: Restore multi-society serving coverage after scoped DAG runs

**Priority:** P0

The serving bundle currently loads only `3` properties, all Godrej Splendour BHK
variants. This makes Whitefield search look functional but too narrow, and it
makes compare collapse into a one-society table.

**Evidence**

- `/api/health` reported serving bundle `2026-07-26T10:10:25Z`.
- `/api/properties` returned only:
  `discovered-godrej-splendour-1bhk`, `discovered-godrej-splendour-2bhk`,
  `discovered-godrej-splendour-3bhk`.
- `/?q=Whitefield` rendered only the three Godrej Splendour cards.

**Request**

Make scoped DAG runs append/promote into the current serving bundle without
dropping previously crawled societies. Add a post-run guard that fails or warns
when a scoped run would reduce active serving-bundle property/society counts
unexpectedly.

**Acceptance**

- Whitefield searches include the recent Waterford, Prestige, Brigade, Sumadhura,
  and Godrej projects that were previously crawled.
- `/api/admin/asset-runs/current` and `/api/health` expose enough bundle-count
  metadata to spot coverage regression immediately.
- Compare can be audited against at least three different societies.

## FR2: Stop stretching low-resolution listing thumbnails

**Priority:** P0

Search and detail pages are rendering MagicBricks thumbnail URLs such as
`Photo_h180_w240` into large cards and hero frames. The UI becomes calm but
visibly soft, especially on mobile where 240x180 images are rendered roughly
358x448 or larger.

**Evidence**

- Search screenshots show all three result cards using the same low-res tower
  image.
- Detail image audit reported `21` images, with many natural sizes below
  `360x220`.
- API images for Godrej Splendour include `Photo_h180_w240` URLs.

**Request**

Prefer locally downloaded high-quality media from the image DAG. Only use
thumbnail listing URLs as placeholders when no better source exists. Store
optimized WebP/JPEG previews locally and serve those refs to the UI.

**Acceptance**

- Result-card and detail hero images have natural dimensions appropriate for the
  rendered slot.
- Duplicate thumbnails are deduped before rendering.
- API exposes enough image metadata for the UI to avoid selecting tiny assets for
  large surfaces.

## FR3: Add lifecycle and RERA numeric search intents

**Priority:** P1

The new configuration intent works, but several RERA-backed user queries still
fall through to weak keyword search.

**Evidence**

- `3BHK projects with floor plans in Whitefield` matched `has_3bhk`,
  `available_configurations`, and RERA floor-plan facts correctly.
- `ready projects Whitefield` returned under-construction homes because `ready`
  was not parsed as a lifecycle constraint.
- `large open area low density` returned weak keyword matches instead of using
  `open_space_pct` and `units_per_acre`.
- `covered parking` returned no results and no interpreted preference.
- `1 year old property` parsed an age constraint but returned no graceful
  alternative or explanation when the current bundle had only under-construction
  inventory.

**Request**

Wire lifecycle synonyms and RERA numeric facts into search intent:

- `ready`, `delivered`, `under construction`, `upcoming`, `delayed`
- `large open area`, `low density`, `acres`, `floor count`, `tower count`
- parking terms such as `covered parking`, `visitor parking`, `EV parking`

Search should use typed facts/enums, not freeform labels.

**Acceptance**

- Ready/delivered queries exclude under-construction projects unless the UI
  clearly shows no exact matches and then presents alternatives.
- Low-density/open-area queries rank by derived RERA numbers.
- Parking queries match only when parking facts exist.

## FR4: Remove internal caveats from buyer-facing evidence values

**Priority:** P1

The detail API still contains buyer-facing values like `visual road-width
verification is pending`. Even when a specific string is not visible in the first
viewport, it is flowing through the evidence contract and can leak as tiles
expand.

**Evidence**

- Detail evidence item `access_road_quality` value:
  `Approach road inferred from Google project coordinates; visual road-width verification is pending.`
- API property tags still include `Source: serving_bundle`, which is an internal
  storage label even if the current cards do not render it prominently.

**Request**

Separate internal enrichment status from buyer evidence text. Buyer views should
show the fact we know, the source, and a quiet confidence/proof affordance, not
pipeline state.

**Acceptance**

- No visible evidence item uses phrases like `pending verification`,
  `serving_bundle`, `pipeline`, `gap`, or `enrichment`.
- Internal status remains available in admin/debug views or DAG health reports.

## FR5: Add a configuration-compare mode when selected homes share a society

**Priority:** P1

The compare page dedupes selected `1BHK`, `2BHK`, and `3BHK` Godrej Splendour
properties into one society row. That is correct for society comparison, but it
does not answer the user's actual action when they selected multiple
configurations.

**Evidence**

- Compare URL with three selected Godrej Splendour BHK IDs rendered one row.
- The page title says `Same budget. Different tradeoffs.`, but the visible table
  has only one society and one active BHK row.

**Request**

Add a mode switch or automatic branch:

- Same society, multiple BHKs: compare configurations, area, price, monthly plan,
  and available floor-plan facts.
- Multiple societies: compare society-level facts such as acres, density, open
  area, lifecycle, and proof strength.

**Acceptance**

- Selecting three BHK variants from one society creates a useful three-row
  configuration comparison.
- Selecting three societies keeps the current society comparison table.

## FR6: Tighten the mobile approach-road carousel

**Priority:** P2

The approach-road drawer is a strong pattern: it opens in-place, shows six road
frames, and avoids a new tab. On mobile, thumbnail labels on the right edge are
clipped and the strip reads like a grid trying to become a carousel.

**Evidence**

- Mobile detail screenshot shows the second thumbnail label truncated at the
  right edge.
- DOM audit flagged overflow in `catalog-card__media alt-paths__media`.

**Request**

Turn the mobile thumbnail area into an explicit horizontal carousel with snap
points, stable tile width, and labels that stay inside each frame.

**Acceptance**

- No thumbnail label clips at 390px width.
- Active frame state is obvious.
- The drawer remains in-page and does not open Google Maps in a new tab for
  normal browsing.

## FR7: Polish EMI plan typography and number formatting

**Priority:** P2

The EMI plan route has the right name and a coherent graph, but the hero is very
large relative to the rest of the page and the financial inputs show awkward
spacing such as `₹ 90 K / mo`.

**Evidence**

- `/property/discovered-godrej-splendour-3bhk/plan` screenshot shows the H1
  dominating the first viewport.
- The input rail displays `₹ 90 K / mo`, `₹ 35 K / mo`, and `₹ 55 K / mo`.

**Request**

Reduce hero scale, make the top summary denser, and use polished compact money
formatting such as `₹90K/mo`.

**Acceptance**

- First viewport shows the verdict, controls, and graph start without feeling
  like a landing hero.
- Money labels are compact and consistent across buy, rent, and SIP controls.

## FR8: Replace `Map unavailable` with a graceful nearby fallback

**Priority:** P2

The detail page currently shows `Map unavailable` with a retry button. For users,
this reads like a broken feature even though nearby places are available.

**Evidence**

- Detail page text includes `Map unavailable` and `Retry map`.
- Nearby places such as schools render below the same section.

**Request**

When the map renderer cannot load, show a compact nearby-list or static fallback
instead of a blank/error state.

**Acceptance**

- Users still get useful nearby context when map tiles fail.
- Retry remains available but is not the main visual object.
